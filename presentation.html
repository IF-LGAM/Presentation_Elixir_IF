Le Routage Phoenix : Scopes, Pipelines & Live Sessions

Coexistence native du Web classique, des APIs REST et des tunnels temps réel

Aiguillage Réseau

Des flux étanches et composables

  • Pipelines modulaires : :browser gère cookies et CSRF ; :api traite du JSON stateless pur.
  • Scopes hiérarchiques : Découpage explicite entre routes publiques, zone authentifiée et API /api.
  • Sécurisation live_session : Le hook ensure_authenticated filtre dès la poignée de main WebSocket.
  • Vérification compilation : Le sigil vérifié ~p interdit toute URL invalide à la compilation.
Garantie BEAM : Chaque requête HTTP ou WebSocket est isolée dans son micro-processus indépendant.
lib/les_bons_comptes_web/router.ex
defmodule LesBonsComptesWeb.Router do
  use LesBonsComptesWeb, :router

  pipeline :browser do
    plug :accepts, ["html"]
    plug :fetch_session
    plug :protect_from_forgery
  end

  pipeline :api do
    plug :accepts, ["json"]
  end

  # Scope Web & LiveView sous session sécurisée
  scope "/", LesBonsComptesWeb do
    pipe_through :browser

    live_session :authenticated_user,
      on_mount: [{UserAuth, :ensure_authenticated}] do
      live "/wallets", WalletLive.Index, :index
      live "/wallets/:id", WalletLive.Show, :show
      live "/wallets/:id/expenses/new", WalletLive.ExpenseNew, :new
    end
  end

  # API REST JSON pour tiers & scripts
  scope "/api", LesBonsComptesWeb do
    pipe_through :api
    get "/wallets/:id/settlements", SettlementController, :index
  end
end
Principe directeur : Un seul fichier pour gouverner tout le trafic : pages HTML, endpoints REST et applications LiveView.

Contrôleurs Standard : Fonctions Pures & Algorithmique Métier

Pattern matching en signature, gestion d'erreurs et calcul des dettes

Paradigme MVC Pur

Une transformation de données immuable

  • Action = Fonction pure : L'action reçoit (conn, params) et renvoie une nouvelle structure conn.
  • Pattern Matching en signature : Déstructuration immédiate de l'identifiant URL (%{"id" => id}).
  • Algorithmique dans le Contexte : Le contrôleur n'exécute pas de SQL, il sollicite Expenses.calculate_settlements/1.
  • Rendu sans exception : Les cas d'erreur (nil) sont gérés par retour de statuts HTTP propres sans crash.
Flux de données pur : Requête HTTP ➔ Router (~p) ➔ Controller ➔ Context Expenses ➔ Réponse JSON
lib/les_bons_comptes_web/controllers/settlement_controller.ex
defmodule LesBonsComptesWeb.SettlementController do
  use LesBonsComptesWeb, :controller
  alias LesBonsComptes.{Expenses, Wallets}

  # 1. Extraction directe de l'identifiant URL
  def index(conn, %{"id" => id}) do
    case Wallets.get_wallet(id) do
      nil ->
        conn
        |> put_status(:not_found)
        |> json(%{error: "Porte-monnaie introuvable"})

      wallet ->
        settlements = Expenses.calculate_settlements(wallet)
        creditors = Expenses.calculate_creditors(wallet)

        render(conn, :index,
          wallet: wallet,
          settlements: settlements,
          creditors: creditors
        )
    end
  end
end
Règle d'or : Zéro état persistant dans le contrôleur : f(conn, params) -> conn. Prévisible, testable et sans effets de bord.

LiveView & PubSub : Collaboration Temps Réel Native

Synchronisation instantanée entre utilisateurs sans Redis ni polling JavaScript

Rupture Technologique

La Triade Réactive de Phoenix

  • 1. Abonnement PubSub : À l'ouverture du WebSocket, le client s'abonne au topic "wallet:#{id}" sur la BEAM.
  • 2. Événement utilisateur : Clic suppression dépense → écriture en base et diffusion instantanée.
  • 3. Réception collective : Tous les participants reçoivent {:wallet_updated, id} et leur vue s'actualise.
  • Diffing chirurgical : Seuls les octets modifiés transitent sur le WebSocket (< 10 ms).
Zéro JavaScript : La BEAM orchestre l'état serveur et pousse les deltas binaires sur WebSocket.
lib/les_bons_comptes_web/live/wallet_live/show.ex
defmodule LesBonsComptesWeb.WalletLive.Show do
  use LesBonsComptesWeb, :live_view
  alias LesBonsComptes.{Expenses, Wallets}

  # 1. Montage et abonnement au canal du porte-monnaie
  def mount(%{"id" => id}, _session, socket) do
    if connected?(socket) do
      Phoenix.PubSub.subscribe(PubSub, "wallet:#{id}")
    end

    wallet = Wallets.get_wallet!(id)
    {:ok, assign(socket, wallet_id: id, wallet: wallet)}
  end

  # 2. Réaction à la suppression d'une dépense
  def handle_event("delete_expense", %{"id" => exp_id}, socket) do
    Expenses.delete_expense(socket.assigns.current_user, exp_id)
    {:noreply, put_flash(socket, :info, "Dépense supprimée")}
  end

  # 3. Notification PubSub reçue par TOUS les participants
  def handle_info({:wallet_updated, wallet_id}, socket) do
    {:ok, data} = load_wallet_data(wallet_id)
    {:noreply, assign(socket, data)}
  end
end
Révolution : Alice supprime une dépense -> l'écran de Bob ajuste ses soldes en direct sans recharger la page et sans une ligne de JS.

Matrice Décisionnelle : Choisir l'Outil Adapté

Pourquoi « Les bons comptes » combine harmonieusement contrôleurs HTTP et LiveView

Contrôleurs Standard (HTTP)

Cas d'Usage Recommandés

  • APIs REST / JSON publiques : Endpoints exposés aux tiers ou applications mobiles (SettlementController).
  • Cookies d'authentification : Écriture sécurisée des en-têtes HTTP de session (UserSessionController).
  • Webhooks externes : Réception des callbacks de passerelles de paiement (Stripe).
  • Téléchargements de fichiers : Streaming de bilans ou d'exports comptables PDF/CSV.
Phoenix LiveView (WebSocket)

Cas d'Usage Privilégiés

  • Interfaces collaboratives : Modification partagée et temps réel de dépenses (WalletLive.Show).
  • Formulaires réactifs : Validation en direct à la frappe sans duplication de code front/back.
  • Tableaux de bord dynamiques : Visualisation instantanée des soldes et des dettes croisées.
  • Productivité maximale : Élimination du boilerplate d'API REST pour la majorité des vues.
Synthèse : Phoenix n'impose aucun dogme : il associe la robustesse du HTTP classique à la réactivité d'une SPA moderne.
